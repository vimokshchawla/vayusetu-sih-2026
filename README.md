# VayuSetu

Fleet predictive-maintenance frontend for SIH26249 (Air Power – Predictive Maintenance & Fleet Availability), connected to the **VayuSetu RUL model v1.1**.

## Run locally

```powershell
npm install
npm run dev
```

Build and lint:

```powershell
npm run build
npm run lint
```

## Where the data comes from

Every page now shows real model output for the 707 NASA C-MAPSS test engines (FD001–FD004):

| File | What it holds | Used by |
|---|---|---|
| `src/data/modelData.ts` | Engines (P10 / median / P90, band, drivers, recommended action), early warnings, model metrics | All pages |
| `public/data/engines/<id>.json` | Per-engine sensor history (normalised within flight condition) and the model's P10 / P50 / P90 at every flight | Engine Diagnostics |

Both are **generated** – do not edit them by hand. When the ML notebook produces new outputs, regenerate them:

```powershell
python tools/build_model_data.py --outputs path\to\vayusetu_outputs --dataset path\to\VayuSetu_final_dataset
```

The script needs pandas and numpy and reads these notebook outputs: `vayusetu_test_predictions.csv`, `vayusetu_history_predictions.csv`, `vayusetu_driver_effects.csv`, `vayusetu_model_card.json`, `vayusetu_model_arena.csv`, `vayusetu_feature_family_ledger.csv`, plus `VayuSetu_train.csv` / `VayuSetu_test.csv`.

## Demo fleet layer (hard-coded, fictional)

The NASA data only has engines, so fleet availability uses a **hard-coded demo fleet**: 12 fictional air bases, 475 fictional aircraft (types VS-F1, VS-F2, VS-T4, VS-J1) and 12 maintenance units. Every one of the 707 real model-scored engines is fitted to a demo aircraft, so all engine numbers stay real. Pages that use it carry a “demo fleet” notice.

| File | What it holds |
|---|---|
| `src/data/fleetDemo.ts` | Bases (name, state, map position, tempo), aircraft (tail, type, base, engines, sortie rate, days in hangar), maintenance units (90-day statistics). Generated by `python tools/build_fleet_demo.py` (fixed seed – same fleet every run). Re-run it after `build_model_data.py`. |
| `src/utils/readiness.ts` | Aircraft status (worst engine decides), days to Critical, expected availability, base summaries. |
| `public/data/india_states.geojson` | **Optional – add it yourself.** Indian state boundaries for the Air Base Map. Copy the file NIRMAN uses (it must follow the official Survey of India boundary). Without it the map shows bases on a plain grid. Property names `st_nm`, `ST_NM`, `NAME_1`, `name` or `state` are recognised. |

Pages using the demo fleet: Air Base Map, Readiness Radar, Maintenance Units, Fleet Analytics, the fleet-availability panel on Overview, and the aircraft readiness CSV in Reports. Header search also accepts tail numbers (e.g. `F2-101`).

## Rules used in the interface

- Risk band from pessimistic P10: RED ≤ 25 cycles, AMBER 26–60, GREEN > 60 (`src/utils/fleet.ts`, same rule as the model).
- Model drivers: sensors that lower predicted life by at least 0.5 cycles compared with a healthy engine in the same flight condition. If none does, the engine shows “None stands out”.
- Early warnings: P10 ≤ 30 cycles on 3 of the last 5 flights (the rule validated in the notebook).
- Aircraft: the worst engine decides status. Ready now = no RED engine and not in the hangar. Days to Critical = (worst P10 − 25) ÷ sorties per day. Expected availability on day h (no maintenance in between) = RED aircraft stay grounded, hangar aircraft return when their work ends, and each engine must not have reached end of life (from its P10 / median / P90).
- Base readiness colours: ≥ 80% ready green, 65–80% amber, < 65% red.
- What-if Planning (`src/pages/WhatIf.tsx`) works on one engine at a time: change sortie tempo, cycles per sortie, a surge period, grounding days or a planned inspection, then compare end-of-life risk within the chosen horizon (baseline vs scenario). Risk is read from the model's P10 / median / P90 range for that engine; the scenario changes how fast that life is used, not the engine's condition. Outlook bands: Stable ≤ 30%, Elevated 30–60%, Severe > 60%. It is not a maintenance schedule.

NASA C-MAPSS is simulated turbofan data, not military maintenance data. Every action needs approval from a certifying engineer.

## Backend integration (later)

`src/services/api.ts` holds the API boundary for a live backend (`VITE_API_BASE_URL`). The app currently reads the bundled model outputs above. To score new sensor data live, the backend loads `vayusetu_rul_pipeline.joblib` and serves the same fields.
